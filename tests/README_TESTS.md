# HeadMotion Test Suite

This document describes the HeadMotion test suite, how to run it, and the environment variables used by the individual tests.

The test suite contains three broad categories:

- **Unit tests** — deterministic, hardware-free tests for small components and helpers.
- **Synthetic integration/stress tests** — hardware-free tests that exercise larger portions of the sync pipeline.
- **Hardware integration tests** — tests that communicate with real MMS+ devices over USB.

> **Warning**
>
> Some hardware tests are destructive. They may stop recording, clear existing logs, recreate logger routes, and reset the MMS+ board. Read the hardware-test sections before running them.

---

## Building and running tests

Tests are enabled through the CMake option:

```text
HEADMOTION_BUILD_TESTS
```

The project Makefile already enables this for the normal test build:

```bash
make test-debug
```

Equivalent CMake configuration:

```bash
cmake -S . -B build/linux-native-debug -G Ninja \
    -DCMAKE_BUILD_TYPE=Debug \
    -DHEADMOTION_SERIAL_BACKEND=native \
    -DHEADMOTION_BUILD_GUI=ON \
    -DHEADMOTION_BUILD_TESTS=ON
```

Then build and run:

```bash
cmake --build build/linux-native-debug
ctest --test-dir build/linux-native-debug --output-on-failure
```

Run one test by name:

```bash
ctest \
    --test-dir build/linux-native-debug \
    -R sync_pairing \
    --output-on-failure
```

Run an executable directly when you want its full verbose output:

```bash
./build/linux-native-debug/headmotion_test_sync_pairing
```

List registered tests:

```bash
ctest --test-dir build/linux-native-debug -N
```

Run tests by label:

```bash
ctest --test-dir build/linux-native-debug -L unit
ctest --test-dir build/linux-native-debug -L sync
ctest --test-dir build/linux-native-debug -L hardware
```

# CMake test variable

## `HEADMOTION_BUILD_TESTS`

Controls whether test executables and CTest entries are generated.

Default:

```text
OFF
```

Enable manually with:

```bash
cmake -S . -B build/linux-native-debug \
    -DHEADMOTION_BUILD_TESTS=ON
```

The project Makefile's `test-debug` target already enables it.

# Hardware-free tests

These tests require no physical MMS+ hardware.

## `sync_large`

Executable:

```text
headmotion_test_sync_large
```

Purpose:

- Exercises the real stateless sync callback/writer path with synthetic data.
- Sends a large number of accelerometer and gyroscope samples.
- Verifies that the queue, writer thread, counters, CSV output, and pairing survive sustained load.

Run:

```bash
ctest \
    --test-dir build/linux-native-debug \
    -R sync_large \
    --output-on-failure
```

### `HEADMOTION_TEST_SYNC_PAIRS`

Controls the number of synthetic accelerometer/gyro sample pairs generated by `sync_large`.

Example:

```bash
HEADMOTION_TEST_SYNC_PAIRS=1000000 \
./build/linux-native-debug/headmotion_test_sync_large
```

If one pair contains one accelerometer callback and one gyroscope callback, then:

```text
1,000,000 pairs = 2,000,000 synthetic IMU callbacks
```

Use this variable to increase stress without changing the source code.

---

## `parallel_sync`

Executable:

```text
headmotion_test_parallel_sync
```

Purpose:

- Hardware-free parallel stress test.
- Creates several independent virtual MMS+ sync sessions.
- Each virtual device has its own sync state, callback queue, writer thread, and CSV outputs.
- Verifies that simultaneous sync operations do not contaminate one another.

Run:

```bash
ctest \
    --test-dir build/linux-native-debug \
    -R parallel_sync \
    --output-on-failure
```

### `HEADMOTION_PARALLEL_DEVICES`

Number of virtual MMS+ devices created by the test.

Example:

```bash
HEADMOTION_PARALLEL_DEVICES=8 \
./build/linux-native-debug/headmotion_test_parallel_sync
```

Typical/default configuration:

```text
4
```

### `HEADMOTION_PARALLEL_PAIRS`

Number of accelerometer/gyro pairs generated **per virtual device**.

Example:

```bash
HEADMOTION_PARALLEL_DEVICES=4 \
HEADMOTION_PARALLEL_PAIRS=200000 \
./build/linux-native-debug/headmotion_test_parallel_sync
```

This produces:

```text
4 devices
× 200,000 pairs/device
= 800,000 paired rows

800,000 pairs
× 2 callbacks/pair
= 1,600,000 IMU callbacks
```

A long-duration synthetic test approximating 3.5 days at 50 Hz can be run with:

```bash
HEADMOTION_PARALLEL_DEVICES=4 \
HEADMOTION_PARALLEL_PAIRS=15120000 \
./build/linux-native-debug/headmotion_test_parallel_sync
```

## `sync_pairing`

Executable:

```text
headmotion_test_sync_pairing
```

Purpose:

- Deterministic unit test for accelerometer/gyro timestamp pairing.
- Tests exact matches.
- Tests the configured pairing tolerance.
- Tests samples just outside the tolerance.
- Tests older accelerometer samples.
- Tests older gyroscope samples.
- Tests multiple queued pairs.
- Tests leftover/unmatched samples.

No environment variables are required.

---

## `sync_queue_overflow`

Executable:

```text
headmotion_test_sync_queue_overflow
```

Purpose:

- Deliberately fills the sync callback queue without running the CSV writer.
- Verifies that `MAX_QUEUED_SAMPLES` is enforced.
- Verifies that queue overflow is reported as an error.
- Verifies that the queue never grows beyond its configured maximum.

This is an intentional failure-condition test. The **CTest test passes** when the queue overflow is correctly detected.

No environment variables are required.

---

## `parallel_failure_isolation`

Executable:

```text
headmotion_test_parallel_failure_isolation
```

Purpose:

- Runs several synthetic sync states simultaneously.
- Introduces failures into selected virtual devices.
- Verifies that a failed sync does not terminate or contaminate unrelated sync operations.

Typical scenario:

```text
virtual device 0 -> normal
virtual device 1 -> writer/disk failure
virtual device 2 -> normal
virtual device 3 -> malformed input
```

Expected logical result:

```text
device 0 -> successful
device 1 -> expected failure detected
device 2 -> successful
device 3 -> expected failure detected
```

The overall CTest test passes when failure isolation behaves correctly.

No environment variables are required unless added to the test later.

---

## `sync_filename_collision`

Executable:

```text
headmotion_test_sync_filename_collision
```

Purpose:

- Tests CSV filename generation.
- Ensures existing files are not overwritten.
- Ensures Xsens, legacy IMU, and battery files use the same session suffix.
- Tests multiple previous sessions.
- Tests filename sanitization.
- Tests different virtual device IDs selecting independent output paths.

Example session filenames:

```text
imu_0561E1.csv
imu_legacy_0561E1.csv
battery_0561E1.csv
```

If that session already exists:

```text
imu_0561E1_1.csv
imu_legacy_0561E1_1.csv
battery_0561E1_1.csv
```

No environment variables are required.

---

## `device_id_sanitization`

Executable:

```text
headmotion_test_device_id_sanitization
```

Purpose:

- Verifies that MMS+ device IDs are safe to use in filenames.
- Removes path traversal characters.
- Replaces unsafe punctuation with underscores.
- Preserves allowed letters, digits, `-`, and `_`.

Examples:

```text
0561E1        -> 0561E1
MMS 123       -> MMS_123
../../../evil -> evil
abc:def/ghi   -> abc_def_ghi
```

No environment variables are required.

---

## `usb_frame_codec`

Executable:

```text
headmotion_test_usb_frame_codec
```

Purpose:

Tests the MMS+ USB framing protocol:

```text
0x1F <length> <payload> 0x0A
```

Coverage includes:

- normal frame encoding/decoding
- empty payloads
- maximum 255-byte payload
- rejection of oversized payloads
- partial frames
- split reads
- several frames in one buffer
- garbage before frames
- invalid terminators
- resynchronization
- framing bytes inside payload data

No environment variables are required.

---

## `command_output_concurrency`

Executable:

```text
headmotion_test_command_output_concurrency
```

Purpose:

- Stresses one shared `CommandOutput`.
- Emits events from many threads.
- Ensures sink invocation remains serialized.
- Verifies no events are lost.
- Verifies JSON lines are not interleaved.
- Verifies escaping of quotes, backslashes, tabs, and newlines.
- Verifies per-producer ordering.

### `HEADMOTION_COMMAND_OUTPUT_THREADS`

Number of producer threads.

Typical/default value:

```text
16
```

Example:

```bash
HEADMOTION_COMMAND_OUTPUT_THREADS=32 \
./build/linux-native-debug/headmotion_test_command_output_concurrency
```

### `HEADMOTION_COMMAND_OUTPUT_EVENTS`

Number of events emitted **per producer thread**.

Typical/default value:

```text
2000
```

Example:

```bash
HEADMOTION_COMMAND_OUTPUT_THREADS=32 \
HEADMOTION_COMMAND_OUTPUT_EVENTS=10000 \
./build/linux-native-debug/headmotion_test_command_output_concurrency
```

That produces:

```text
32 × 10,000 = 320,000 events
```

# Hardware tests

Hardware tests return exit code `77` when their required hardware configuration is not supplied. CTest interprets this as:

```text
Skipped
```

This means normal development runs such as:

```bash
make test-debug
```

can include the hardware targets without automatically modifying a connected MMS+.

Hardware tests are also configured with:

```text
RUN_SERIAL TRUE
```

so CTest does not run them alongside another test.

---

## `parallel_operations_hw`

Executable:

```text
headmotion_test_parallel_operations
```

Purpose:

- Real-hardware concurrency test.
- Requires at least two MMS+ devices.
- Runs operations against physical devices simultaneously.
- Intended specifically for testing multi-device concurrency.

This is different from `hardware_multi_device_e2e`, which tests devices sequentially.

### `HEADMOTION_TEST_PORTS`

Comma-separated list of physical MMS+ serial ports.

Example:

```bash
HEADMOTION_TEST_PORTS="/dev/serial/by-id/mms1,/dev/serial/by-id/mms2" \
./build/linux-native-debug/headmotion_test_parallel_operations
```

At least two ports are required.

If fewer than two ports are supplied, the test returns `77` and is skipped.

# Single-device hardware E2E

CTest name:

```text
hardware_single_device_e2e
```

Executable:

```text
headmotion_test_hardware_single_device_e2e
```

This is a **destructive** hardware integration test.

It performs the full real MMS+ lifecycle:

```text
identify
  ↓
record-reset
  ↓
wait for USB re-enumeration
  ↓
record-start at 50 Hz
  ↓
record real samples
  ↓
record-stop
  ↓
sync/download
  ↓
validate CSV output
  ↓
record-reset
  ↓
verify device returns
```

The test validates:

- real USB communication
- MetaWear SDK initialization
- logger creation
- onboard flash logging
- accel/gyro collection
- record-stop
- anonymous logger discovery
- log download
- callback handling
- accel/gyro pairing
- CSV writer behavior
- packet counters
- CSV row counts
- device-ID-based filenames
- final board reset

## `HEADMOTION_HW_E2E_PORT`

Required serial port for the physical MMS+.

Prefer a stable `/dev/serial/by-id/...` path instead of `/dev/ttyACM0`, because the test resets the board and USB may re-enumerate.

Example:

```bash
HEADMOTION_HW_E2E_PORT="/dev/serial/by-id/<MMS_DEVICE>" \
./build/linux-native-debug/headmotion_test_hardware_single_device_e2e
```

If the variable is not set, the test is skipped.

## `HEADMOTION_HW_E2E_SECONDS`

Recording duration in seconds.

Default:

```text
5
```

Example:

```bash
HEADMOTION_HW_E2E_PORT="/dev/serial/by-id/<MMS_DEVICE>" \
HEADMOTION_HW_E2E_SECONDS=30 \
./build/linux-native-debug/headmotion_test_hardware_single_device_e2e
```

At 50 Hz, a 5-second recording nominally produces approximately:

```text
250 accelerometer samples
250 gyroscope samples
250 paired Xsens rows
```

The actual count may be slightly higher because the MMS+ continues logging while `record-stop` initializes and sends its stop commands.

## `HEADMOTION_HW_E2E_BATTERY_INTERVAL`

Battery logging interval in seconds.

Default:

```text
0
```

A value of `0` disables battery logging.

Example:

```bash
HEADMOTION_HW_E2E_PORT="/dev/serial/by-id/<MMS_DEVICE>" \
HEADMOTION_HW_E2E_SECONDS=10 \
HEADMOTION_HW_E2E_BATTERY_INTERVAL=1 \
./build/linux-native-debug/headmotion_test_hardware_single_device_e2e
```

This enables a battery sample approximately once per second during recording and validates the resulting battery CSV.

# Multi-device hardware E2E

CTest name:

```text
hardware_multi_device_e2e
```

Executable:

```text
headmotion_test_hardware_multi_device_e2e
```

This test is also **destructive**.

Unlike `parallel_operations_hw`, the MMS+ devices are tested **sequentially**.

For example:

```text
Device 0:
    identify
    reset
    record
    stop
    sync
    validate
    reset

Device 1:
    identify
    reset
    record
    stop
    sync
    validate
    reset

Device 2:
    ...
```

This test answers:

> Can HeadMotion complete the entire recording lifecycle against several different physical MMS+ devices?

It does **not** test concurrent hardware operation.

After all devices finish, it performs cross-device checks for:

- unique physical identities
- unique output device IDs
- unique CSV output paths
- successful recording/download on every board

## `HEADMOTION_HW_E2E_PORTS`

Required comma- or semicolon-separated list of MMS+ ports.

At least two are required.

Example:

```bash
HEADMOTION_HW_E2E_PORTS="/dev/serial/by-id/mms1,/dev/serial/by-id/mms2" \
./build/linux-native-debug/headmotion_test_hardware_multi_device_e2e
```

Three devices:

```bash
HEADMOTION_HW_E2E_PORTS="/dev/serial/by-id/mms1,/dev/serial/by-id/mms2,/dev/serial/by-id/mms3" \
./build/linux-native-debug/headmotion_test_hardware_multi_device_e2e
```

The test rejects duplicate port strings.

Again, prefer `/dev/serial/by-id/...` paths because each board is reset during the test.

## `HEADMOTION_HW_E2E_SECONDS`

Same meaning as the single-device test.

Controls recording duration **for each device**.

Default:

```text
5
```

Example:

```bash
HEADMOTION_HW_E2E_PORTS="/dev/serial/by-id/mms1,/dev/serial/by-id/mms2" \
HEADMOTION_HW_E2E_SECONDS=10 \
./build/linux-native-debug/headmotion_test_hardware_multi_device_e2e
```

With two devices, each board records for 10 seconds independently.

## `HEADMOTION_HW_E2E_BATTERY_INTERVAL`

Same meaning as the single-device test.

Default:

```text
0
```

A value of `0` disables battery logging.

Example:

```bash
HEADMOTION_HW_E2E_PORTS="/dev/serial/by-id/mms1,/dev/serial/by-id/mms2" \
HEADMOTION_HW_E2E_SECONDS=10 \
HEADMOTION_HW_E2E_BATTERY_INTERVAL=1 \
./build/linux-native-debug/headmotion_test_hardware_multi_device_e2e
```

| `HEADMOTION_HW_E2E_BATTERY_INTERVAL` | hardware E2E tests | `0` | Battery sample interval; `0` disables battery logging |

```bash

    --test-dir build/linux-native-debug \
    -L unit \
    --output-on-failure
```

```bash

    --test-dir build/linux-native-debug \

    --output-on-failure
```

```bash
    --test-dir build/linux-native-debug \
```

```bash
ctest \
    --test-dir build/linux-native-debug \
```

# Test philosophy

The suite intentionally separates different failure domains.

## Unit tests

Use deterministic inputs and should be fast:

```text
sync_pairing
sync_queue_overflow
device_id_sanitization
usb_frame_codec
command_output_concurrency
```

These should identify specific logic regressions.

## Synthetic integration tests

Exercise larger portions of the real implementation without requiring hardware:

```text
sync_large
parallel_sync
parallel_failure_isolation
sync_filename_collision
```

These are useful for load, concurrency, queue, writer, and isolation regressions.

## Hardware integration tests

Exercise actual MMS+ boards:

```text
parallel_operations_hw
hardware_single_device_e2e
hardware_multi_device_e2e
```

These catch problems that synthetic tests cannot reproduce, including:

- USB CDC behavior
- device reset/re-enumeration
- MetaWear SDK initialization
- real logger creation
- flash logging
- anonymous logger discovery
- physical log download
- device identity handling

Keeping these categories separate makes failures easier to diagnose.

For example:

```text
sync_pairing fails
    -> pairing algorithm regression

parallel_sync fails
    -> host-side sync/concurrency regression

hardware_single_device_e2e fails
while synthetic tests pass
    -> likely USB / SDK / firmware / hardware integration issue

single-device hardware passes
but parallel_operations_hw fails
    -> likely real multi-device concurrency issue

single-device passes
but one device in hardware_multi_device_e2e fails
    -> likely device-specific hardware/configuration issue
```

# Hardware safety notes

Before running a destructive hardware test:

1. Make sure there is no recording on the MMS+ that you still need.
2. Prefer stable `/dev/serial/by-id/...` paths.
3. Do not unplug the board while the test is resetting or downloading.
4. Failed test artifacts are intentionally useful for debugging; inspect the printed temporary output directory before deleting them.
5. Use the sequential multi-device E2E test when validating several individual boards.
6. Use `parallel_operations_hw` only when specifically testing simultaneous physical-device behavior.
